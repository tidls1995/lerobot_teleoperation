## 1. 목적과 범위

### 목적

작업대에 설치된 SO-101 팔로워 암 2대를, 원격지(집)의 조종자가 리더 암 2대와 카메라 영상만으로 실시간 조작한다. 1차 용도는 **실험실 장비 조작**이며, 실수 비용이 높다(시료 손상, 장비 파손). 따라서 지연·안정성·안전이 최우선이고 데이터셋 기록은 목표가 아니다.

### MVP 범위

- 조종자 **1명**, 리더 암 2대 → 팔로워 암 2대 (양팔)
- 카메라 3대: 정면 전경 1대 + 각 팔로워 손목 1대씩
- 작업대 = 서버(공인 IP + 포트포워딩), 집 = 클라이언트
- 초기 운영은 작업대 옆에 사람이 있는 상태를 가정하되, **무인 운영으로 갈 수 있는 안전 설계**를 1차부터 포함한다

### 비범위 (후속 스펙)

- 다중 사용자(3명) 세션 관리, 점유 대기열, 인증/권한
- 데이터셋 기록(LeRobotDataset), 정책 학습
- 힘 피드백(리더 암에 저항 전달)
- 자동 복귀·자율 동작

### 설계 원칙

1. **안전 로직은 하드웨어·네트워크 없이 테스트 가능해야 한다.** 실험실 장비 앞에서 처음 시험하는 상황을 만들지 않는다.
2. **최신성 > 완전성.** 낡은 제어값과 낡은 영상 프레임은 버린다.
3. **자동 복구 금지.** 이상 상태에서 사람의 명시적 판단 없이 로봇이 다시 움직이지 않는다.
4. **확장 지점만 열어두고 구현하지 않는다.** 다중 사용자는 구조만 방해하지 않으면 된다.

## 2. 텔레오퍼레이션의 동작 원리 (배경)

SO-101의 관절 6개에는 Feetech STS3215 서보모터가 들어 있다. 모터 6개가 하나의 시리얼 버스를 데이지체인으로 공유하며, USB-TTL 변환보드를 통해 PC의 COM 포트로 노출된다.

| | 리더 암 | 팔로워 암 |
|---|---|---|
| 토크 | 끔 (손으로 자유롭게 움직임) | 켬 (명령 각도를 유지) |
| 우리가 하는 일 | `Present_Position` 읽기 | `Goal_Position` 쓰기 |

로컬 텔레오퍼레이션의 전부는 다음 루프다.

```python
while True:
    angles = leader.read_positions()   # 12개 (양팔)
    follower.write_positions(angles)
    sleep(1/60)
```

**원격화란 이 루프를 가운데서 자르고 그 자리에 네트워크를 넣는 것**이다. 오가는 데이터는 관절각 12개뿐이다. 로봇 제어 로직 자체는 로컬과 동일하다.

원격이 되면서 로컬에서 공짜였던 것이 깨진다.

| 로컬에서 공짜였던 것 | 원격에서 깨지는 방식 | 대응 |
|---|---|---|
| 팔을 눈으로 봄 | 안 보임 | 카메라 3대 |
| 대입문은 100% 즉시 성공 | 유실·지연·순서 뒤바뀜 | UDP + 시퀀스 번호 + 클램프 |
| 이상하면 손으로 잡음 | 개입 불가 | 워치독 → HOLD |
| 두 팔이 같은 자세에서 시작 | 각자 다른 자세 | 정렬 절차 |

## 3. 시스템 구성

```
   집 (클라이언트)                        작업대 (서버, 공인 IP)
┌──────────────────────┐              ┌──────────────────────────┐
│  home/client.py      │              │  workbench/server.py     │
│                      │              │                          │
│  [리더 읽기 스레드]   │ ──UDP:5555──▶│ [제어 스레드]            │
│   USB×2, 60Hz        │              │  안전 게이트 → 팔로워×2  │
│                      │◀─UDP 응답────│  (실제 각도 + 상태 회신)  │
│  [영상 수신 스레드]   │              │                          │
│                      │◀─TCP:5556────│ [영상 스레드×3]          │
│  [화면/입력 메인루프] │              │  캡처 → JPEG → 송신      │
└──────────────────────┘              └──────────────────────────┘
```

### 포트

| 포트 | 프로토콜 | 방향 | 용도 |
|---|---|---|---|
| 5555 | UDP | 양방향 | 제어(집→작업대) + 텔레메트리(작업대→집) |
| 5556 | TCP | 작업대→집 | 영상 3채널 다중화 |

작업대 공유기에 이 2개만 포트포워딩한다. 집 쪽은 클라이언트가 먼저 접속하므로 NAT 테이블이 자동 생성되어 설정이 필요 없다. UDP NAT 매핑은 무통신 시 30초~2분에 만료되지만, 제어 채널은 60Hz로 상시 송신하므로 만료되지 않는다.

Windows 방화벽에 인바운드 허용 규칙이 필요하다.

### 채널 분리 근거

제어와 영상은 요구사항이 정반대다.

| | 제어 | 영상 |
|---|---|---|
| 데이터 단위 | 66바이트 (패킷 1개, MTU 미만 → 절대 분할 안 됨) | ~12KB (패킷 약 9개) |
| 낡은 데이터의 가치 | **0** (다음 패킷에 최신값이 옴) | 프레임 자체는 완결되어야 함 |
| 유실 대응 | 버리고 다음 것 | 재전송 필요 |
| **선택** | **UDP** | **TCP** |

제어를 TCP에 태우면 유실 패킷의 재전송을 기다리느라 이미 도착한 최신 패킷이 대기하고(head-of-line blocking), 팔이 멈췄다가 튀는 움직임이 된다. 영상을 UDP에 태우면 JPEG 조각 재조립·유실 처리를 직접 구현해야 하는데, 이는 TCP를 다시 만드는 일이다.

두 채널을 같은 연결에 태우면 영상 혼잡이 제어를 밀어낸다. 반드시 분리한다.

### 대역폭

320×240 JPEG(q80) ≈ 12KB/프레임 × 15fps × 3대 ≈ **4.3 Mbps**. 작업대 회선 410Mbps 대비 1% 수준. 30fps로 올려도 8.6Mbps이므로 프레임레이트는 설정값으로 두고 현장에서 조정한다.

### 루프 레이트

| 루프 | 주기 | 근거 |
|---|---|---|
| 리더 읽기 → 송신 | 60 Hz | lerobot 은 `sync_read` 로 6개 모터를 **한 번에** 읽는다(왕복 6회가 아니다). 실제 상한은 2단계에서 측정해 확정한다 |
| 팔로워 적용 | 수신 즉시 | 별도 보간 없이 안전 게이트만 통과 |
| 카메라 캡처/전송 | 15 Hz (설정값) | 위 대역폭 계산 |
| 워치독 검사 | 20 Hz | 200ms 임계값을 4샘플로 판정 |

## 4. 프로토콜 명세

모든 필드는 리틀엔디안, 정렬 패딩 없음(`struct` 포맷 문자열 접두 `<`).

### 4.1 제어 패킷 (집 → 작업대, UDP, 60Hz, 66바이트)

```
FORMAT = "<4sIdBB12f"
```

| 오프셋 | 필드 | 크기 | 타입 | 설명 |
|---|---|---|---|---|
| 0 | `magic` | 4 | `4s` | `b"RT01"`. 불일치 시 파싱하지 않고 폐기 |
| 4 | `seq` | 4 | `I` uint32 | 1씩 증가. 되감김 처리 필요 |
| 8 | `t_send` | 8 | `d` float64 | 송신 시각(epoch 초) |
| 16 | `clutch` | 1 | `B` uint8 | 0=해제, 1=engage 요청 |
| 17 | `cmd` | 1 | `B` uint8 | 0=없음, 1=RESET(HOLD 해제 요청). 2~255 예비 |
| 18 | `joints` | 48 | `12f` float32 | 리더 관절각(도) |
| | **합계** | **66** | | |

`cmd`는 `clutch`와 달리 상태 전이를 요청하는 **명령**이다. `RESET`은 HOLD 상태에서만 유효하며 다른 상태에서는 무시한다. 오조작 방지를 위해 클라이언트는 R키를 3초간 길게 눌렀을 때만 `cmd=1`을 실어 보낸다.

### 4.2 텔레메트리 패킷 (작업대 → 집, UDP, 60Hz, 66바이트)

```
FORMAT = "<4sIdBB12f"
```

| 오프셋 | 필드 | 크기 | 타입 | 설명 |
|---|---|---|---|---|
| 0 | `magic` | 4 | `4s` | `b"RT01"` |
| 4 | `seq_echo` | 4 | `I` | 방금 처리한 제어 패킷의 `seq`를 그대로 반향 |
| 8 | `t_send` | 8 | `d` | 서버 송신 시각 |
| 16 | `state` | 1 | `B` | 상태머신 상태 (§5.1) |
| 17 | `flags` | 1 | `B` | 경고 비트마스크 (§4.4) |
| 18 | `joints` | 48 | `12f` | 팔로워 **실제** 관절각(도) |
| | **합계** | **66** | | |

### 4.3 관절 인덱스 (프로토콜의 일부)

`common/protocol.py`에 상수로 정의하며 양쪽이 동일하게 import 한다.

```
[ 0] left_shoulder_pan     [ 6] right_shoulder_pan
[ 1] left_shoulder_lift    [ 7] right_shoulder_lift
[ 2] left_elbow_flex       [ 8] right_elbow_flex
[ 3] left_wrist_flex       [ 9] right_wrist_flex
[ 4] left_wrist_roll       [10] right_wrist_roll
[ 5] left_gripper          [11] right_gripper
```

**단위 (lerobot 실측 확인, 2026-07-31):**

| 인덱스 | 관절 | 단위 | 범위 |
|---|---|---|---|
| 0~4, 6~10 | 몸통 관절 10개 | **도(degree)** | 대략 ±180 |
| **5, 11** | **그리퍼 2개** | **퍼센트 0~100** | 0=닫힘, 100=열림 |

lerobot의 `SOFollower`/`SOLeader`는 `use_degrees=True`일 때 몸통 관절만 `MotorNormMode.DEGREES`를 쓰고, **그리퍼는 항상 `MotorNormMode.RANGE_0_100`**이다. 와이어 포맷은 float32 12개로 동일하지만 5번과 11번의 의미가 다르므로, 안전 임계값과 관절 한계를 이 단위에 맞춰 따로 정해야 한다(§5.4, §7.1).

float32의 유효숫자 7자리는 두 단위 모두에서 서보 분해능(4096스텝/360도 = 0.088도)보다 훨씬 정밀하므로 충분하다.

### 4.4 flags 비트마스크

```python
SPEED_CLAMPED = 1 << 0   # 속도 클램프 작동 중
JOINT_LIMITED = 1 << 1   # 관절 한계 클램프 작동 중
FOLLOW_ERROR  = 1 << 2   # 추종 오차 경고 (아직 HOLD는 아님)
WATCHDOG      = 1 << 3   # 워치독 발동
MOTOR_ERROR   = 1 << 4   # 서보 통신 실패
# 비트 5~7 예비
```

`SPEED_CLAMPED`가 지속되면 조종자가 리더를 팔로워가 따라올 수 있는 속도보다 빠르게 움직이고 있다는 뜻이므로 화면에 경고를 띄운다.

### 4.5 영상 프레임 (작업대 → 집, TCP)

TCP는 메시지 경계를 보존하지 않는 바이트 스트림이므로 **length-prefixed framing**을 사용한다.

```
FORMAT = "<4sBIdI"   # 21바이트 고정 헤더
```

| 오프셋 | 필드 | 크기 | 타입 | 설명 |
|---|---|---|---|---|
| 0 | `magic` | 4 | `4s` | `b"RTV1"` |
| 4 | `cam_id` | 1 | `B` | 0=정면, 1=왼손목, 2=오른손목 |
| 5 | `seq` | 4 | `I` | 카메라별 독립 카운터 |
| 9 | `t_capture` | 8 | `d` | 캡처 시각 |
| 17 | `length` | 4 | `I` | 뒤따르는 JPEG 바이트 수 |
| 21 | `jpeg` | 가변 | | JPEG 데이터 |

수신 측은 `recv_exactly(n)` 헬퍼로 정확히 n바이트를 모을 때까지 반복 수신한다. `recv(n)`은 n보다 적게 반환할 수 있다.

**연결 방향:** 작업대가 5556에서 `listen`하고 **클라이언트가 접속한다.** 데이터는 작업대→집 단방향으로 흐르지만, 포트포워딩이 작업대에만 설정되어 있으므로 연결 개시는 집에서 해야 한다. 서버는 동시에 한 클라이언트만 받으며, 새 연결이 오면 기존 연결을 끊는다(재접속 시 유령 연결이 남지 않게).

### 4.6 버전 협상

`magic` 불일치 패킷은 파싱하지 않고 폐기하며, 서버는 이를 로그에 남긴다. 프로토콜 구조를 변경하면 `RT01` → `RT02`로 올린다. 이는 양쪽 `protocol.py` 버전이 어긋났을 때 바이트를 오해석해 팔에 엉뚱한 각도를 쓰는 사고를 막는 최종 방어선이다.

배포 시에는 폴더 전체를 동기화하여 애초에 어긋나지 않게 한다(§8).

### 4.7 시퀀스 번호 처리

```python
if seq <= last_seq:
    return              # 순서 뒤바뀐 낡은 패킷 폐기
lost = seq - last_seq - 1   # 유실 개수 (통계·화면 표시용)
last_seq = seq
```

UDP는 순서를 보장하지 않는다. 낡은 패킷을 적용하면 팔로워가 앞뒤로 진동한다.

### 4.8 지연 측정

`t_send`로 편도 지연을 계산해서는 **안 된다.** 두 PC의 시계가 동기화되어 있지 않다.

RTT는 반향 방식으로 측정한다. 두 시각 모두 클라이언트 자신의 시계에서 재므로 시계 동기화가 불필요하다.

```python
sent_at[seq] = time.monotonic()          # 송신 시
rtt = time.monotonic() - sent_at[seq_echo]   # 반향 수신 시
```

영상 지연은 `t_capture`를 쓰므로 시계 오차의 영향을 받는다. 절대값이 아니라 **변화 추이**를 보는 용도로만 화면에 표시하고, 오래된 프레임 폐기 판단은 서버 자신의 시계 안에서 수행한다.

## 5. 안전 설계

안전 장치가 막는 사고를 세 범주로 분류한다. 물리·상태 범주는 네트워크가 완벽해도 발생하며, 실제 장비 파손에 더 가깝다.

| # | 사고 | 범주 | 방어 |
|---|---|---|---|
| 1 | 패킷 순서 뒤바뀜 → 팔 진동 | 네트워크 | `seq` |
| 2 | 유실 후 몰아서 도착 → 급가속 | 네트워크 | 속도 클램프 |
| 3 | 인터넷 끊김 → 마지막 명령 유지 | 네트워크 | 서버 워치독 → HOLD |
| 4 | 영상 정지를 모르고 계속 조작 | 네트워크 | 클라이언트 워치독 |
| 5 | 영상이 점점 밀려 과거 화면을 봄 | 네트워크 | 오래된 프레임 폐기 |
| 6 | 팔이 걸렸는데 모터가 계속 밀어붙임 | 물리 | 추종 오차 감시 → HOLD |
| 7 | 팔이 자기 몸통·작업대를 침 | 물리 | 관절 한계 |
| 8 | 접속 순간 팔로워가 순간이동 | 상태 | 정렬 절차 |
| 9 | 리더를 놓아 중력에 쓰러짐 → 팔로워도 쓰러짐 | 상태 | 클러치 |
| 10 | 버전 불일치로 바이트 오해석 | 상태 | `magic` |

### 5.1 상태머신

```
      [DISCONNECTED]
            │ 유효한 제어 패킷 수신
            ▼
       [ALIGNING] ◀───────────┐
            │                 │ 클러치 해제
            │ 전 관절 오차<3도 │
            │  AND 클러치=1    │
            ▼                 │
       [ENGAGED] ─────────────┘         ▲
            │                            │ 도착
            │ 워치독 / 모터에러 / 추종오차  │
            ▼                        [HOMING]
         [HOLD] ── 사람이 명시적 리셋 ──────┘
                   (home_pose 미설정 시 곧바로 ALIGNING)
```

`FAULT`(=4)는 서버 자체 오류(서보 버스 초기화 실패 등) 표현용으로 예약하며, 진입 시 토크를 끄고 사람 개입 없이는 벗어나지 않는다.

### 5.1.1 HOMING — 리셋이 팔로워를 home 자세로 되돌린다

**실물에서 부딪힌 문제 (2026-07-31):** HOLD 가 걸린 자세가 리더로 **물리적으로 도달 불가능**하면 정렬 절차를 통과할 방법이 없다. 실측 사례는 리더의 손잡이가 책상에 닿아 팔로워의 `wrist_roll` 각도까지 돌릴 수 없었던 것이다.

작업대에 사람이 있으면 팔로워를 손으로 돌려 해결되지만, **3단계 이후 원격에서는 집에 있는 사람이 팔로워를 만질 수 없다.** 그러면 HOLD 한 번으로 조종이 영구히 불가능해진다.

그래서 `cmd=RESET` 은 `HOMING` 으로 들어가고, 팔로워를 설정된 `home_pose` 로 **천천히** 되돌린다.

| 항목 | 값 | 근거 |
|---|---|---|
| 이동 속도 | `homing_max_step` 기본 0.5/프레임 (30도/초) | 조종(90도/초)보다 느리게. 먼 거리를 움직이고 조종자가 팔을 안 보고 있을 수 있다 |
| 완료 판정 | 전 관절이 `homing_tolerance`(1.0) 안 | 명령각 기준. 실제각은 뒤따라온다 |
| 이동 조건 | **클러치를 누르고 있는 동안만** | 이 시스템에서 팔이 저절로 움직이는 경우를 만들지 않는다 |
| 진입 직후 | 클러치가 이미 눌려 있어도 움직이지 않음 | 상승 에지를 요구한다. 리셋 직후 팔이 갑자기 가는 것을 막는다 |
| 걸림 감지 | 추종 오차 감시가 ENGAGED 와 동일하게 적용 | 호밍 중 걸렸을 때 계속 밀어붙이면 기어가 갈린다 |
| 워치독 | ALIGNING·ENGAGED 와 동일하게 적용 | 호밍 중 통신이 끊기면 HOLD |
| **그리퍼** | **움직이지 않는다** | 아래 참조 |

**호밍은 그리퍼를 건드리지 않는다.** 팔로워가 시료를 쥔 채 HOLD 가 걸릴 수 있는데, 그때 리셋하면 목표값이 닫힌 쪽이면 **쥔 것을 더 조이고** 열린 쪽이면 **떨어뜨린다.** 둘 다 나쁘다. 쥔 것은 그대로 두는 것이 맞다.

호밍의 목적은 "리더가 도달할 수 있는 자세로 되돌리기"인데 **그리퍼는 도달성과 무관하다** — 리더의 트리거는 손가락으로 0~100 어디든 쉽게 간다. 따라서 그리퍼를 빼도 정렬 절차에 문제가 없다.

완료 판정에서도 그리퍼를 뺀다. 넣으면 영원히 도달하지 못해 호밍이 끝나지 않는다. 다만 **감시에서는 빼지 않는다** — 쥐고 있던 것을 놓쳐 그리퍼가 명령각에서 벗어나면 그것도 이상 상황이므로 추종 오차가 잡는다.

설정의 `home_pose` 는 여전히 관절 12개를 모두 요구하지만 **그리퍼 두 값은 사용되지 않는다.**

**`home_pose` 는 리더에서 떠온다.** 팔로워에서 읽으면 리더가 도달 못 하는 자세를 목표로 삼게 되어 같은 문제가 반복된다. 캘리브레이션이 4대 모두 일치하면 리더 각도와 팔로워 각도는 같은 물리 자세를 가리키므로 그대로 쓸 수 있다. 도구: `python -m tools.capture_home_pose`.

설정 검증에서 `home_pose` 가 `joint_limits` 밖이면 기동을 거부한다 — 클램프에 걸려 영원히 도착하지 못하고 호밍이 끝나지 않기 때문이다.

`home_pose` 를 설정하지 않으면 리셋은 예전처럼 곧바로 `ALIGNING` 으로 간다.

| 상태 | 값 | 팔로워 모터 | 화면 | 진입 조건 |
|---|---|---|---|---|
| DISCONNECTED | 0 | 토크 끔 | 회색 | 서버 기동 직후, 첫 접속 전 |
| ALIGNING | 1 | 토크 켬, 제자리 유지 | 관절별 오차 막대 | 유효 패킷 수신 |
| ENGAGED | 2 | 토크 켬, 리더 추종 | 초록 테두리 | 오차<3도 AND 클러치=1 |
| HOLD | 3 | 토크 켬, **마지막 적용각** 고정 | 빨간 테두리 + 사유 | 워치독/모터에러/추종오차 |
| FAULT | 4 | 토크 끔 | 빨간 화면 | 서버 내부 오류 |

**DISCONNECTED에서 토크를 끄는 이유:** 아무도 조종하지 않는 팔이 힘을 주고 서 있을 이유가 없고, 작업대의 사람이 손으로 팔을 치울 수 있어야 한다.

**HOLD가 마지막 적용각을 유지하는 이유:** 실제각이 아니라 명령각을 유지해야 한다. 실제각을 목표로 잡으면 걸림 상태에서 걸린 자세를 목표로 고정해버린다.

**HOLD는 DISCONNECTED로 내려가지 않는다.** 클라이언트가 완전히 종료되어도 HOLD에 머물며 토크를 유지한다. 팔이 무언가를 쥐고 있거나 들어 올린 상태일 수 있는데 토크를 끄면 그대로 떨어뜨리기 때문이다. 벗어나는 유일한 경로는 `cmd=RESET`이다. 즉 DISCONNECTED는 **서버 기동 직후 한 번만** 존재하는 상태이며, 이후에는 도달하지 않는다.

### 5.2 정렬 절차 (ALIGNING → ENGAGED)

전이 조건: **12개 관절 전부** `|리더각 − 팔로워 실제각| < 3.0도` **AND** `clutch`의 **상승 에지**(0→1)

클러치는 "눌려 있음"이 아니라 **"눌리는 순간"**으로 판정한다. 조종자가 클러치를 누른 채 리더를 휘두르다 우연히 오차가 임계값 안으로 들어오면 의도치 않게 engage된다. 초록 상태를 확인한 **뒤에** 눌러야 하도록, 이미 눌려 있던 클러치는 무시하고 놓았다 다시 눌러야 한다.

접속 시점에 집의 리더와 작업대의 팔로워는 전혀 다른 자세일 수 있다. 어깨 관절이 리더 −80도, 팔로워 +10도라면 오차 90도다. 이 상태에서 즉시 추종을 시작하면 팔로워가 90도 이동 명령을 받아 폭력적으로 휘둘러진다.

클라이언트는 관절 12개의 오차 막대를 표시하고, 조종자가 리더를 손으로 움직여 팔로워 자세에 맞춘다. 전부 임계값 안에 들어오면 막대가 초록으로 바뀌고 그때 클러치를 누를 수 있다.

**임계값 3도의 근거:** engage 순간 팔로워가 이동해야 하는 최대 거리가 3도로 제한된다. 속도 클램프(1.5도/프레임) 기준 최대 2프레임(33ms)에 걸쳐 완료되므로 사실상 움직이지 않는 것과 같다. 설정값으로 노출한다.

**전제:** 리더와 팔로워의 캘리브레이션이 일치해야 한다(§7.2). 캘리브레이션이 어긋나면 "리더의 0도"와 "팔로워의 0도"가 다른 물리적 자세를 가리키므로 정렬 절차 자체가 무의미해진다.

### 5.3 클러치

조종자가 스페이스바를 **누르고 있는 동안에만** `clutch=1`. 놓는 즉시 ENGAGED → ALIGNING으로 전이하고 팔로워는 그 자리에 정지한다.

**구현 제약:** 이 "누르고 있는 동안" 판정에는 키를 뗀 이벤트(KEYUP)가 필요하다. OpenCV의 `waitKey`는 키 눌림만 보고하고 뗌은 감지하지 못하므로 HUD에 사용할 수 없다. **HUD는 pygame으로 구현**하며, OpenCV는 JPEG 인코딩/디코딩과 카메라 캡처에만 사용한다(headless 빌드에서도 동작). 나중에 풋페달을 도입할 경우 pygame의 조이스틱 입력으로 확장한다.

리더 암은 토크가 꺼져 있으므로 손을 놓으면 중력에 쓰러진다. 클러치가 없으면 팔로워도 함께 쓰러지며 장비를 쓸어버린다. 다시 잡았을 때 자세가 달라져 있으므로 ALIGNING을 다시 거치는 것이 자연스러운 흐름이다.

### 5.4 클램프 (ENGAGED에서 매 프레임)

```python
def clamp(x, lo, hi):
    return max(lo, min(x, hi))
```

**(1) 속도 제한** — 기본 1.5도/프레임 (60Hz 기준 **90도/초**)

```python
delta = clamp(target - last_applied, -max_step, +max_step)
applied = last_applied + delta
```

30도에서 50도 명령이 오면 31.5 → 33 → ... → 50으로 약 14프레임(233ms)에 걸쳐 도달한다.

막는 사고: 회선 단절 중 조종자가 리더를 계속 움직였다면, 복구 후 첫 패킷은 30도 떨어진 위치를 담고 있다. 클램프가 없으면 16ms 만에 30도(초당 1800도)를 회전한다.

**90도/초를 선택한 이유:** 실험실 장비 조작은 빠른 동작이 필요 없고, 예기치 않은 움직임의 피해가 크다. 90도/초는 사람이 보고 반응할 수 있는 속도이며, 조종자가 리더를 급하게 움직이면 `SPEED_CLAMPED` 플래그가 켜져 화면에 경고가 뜬다. 이 경고가 자주 뜨면 값을 올리는 것이 아니라 **조종을 천천히 하는 쪽**이 맞다. 2단계 실기 검증에서 실사용 감각을 확인하고 조정한다.

**(2) 관절 한계** — 관절별 min/max를 설정 파일에 지정하고 클램프한다. SO-101의 기구학적 한계보다 보수적으로, 실제 장비 배치를 보고 결정한다. 자기 몸통이나 작업대를 치는 자세를 배제하는 것이 목적이다. `lerobot-find-joint-limits` 로 실측한 값을 출발점으로 삼는다.

**그리퍼는 단위가 퍼센트(0~100)이므로** 한계도 `[0, 100]` 범위 안에서 정한다(§4.3). 속도 클램프 1.5/프레임은 그리퍼에서 "초당 90% 개폐"를 뜻하는데 이는 실사용에 지나치게 느릴 수 있어, 그리퍼만 별도 `max_step` 을 두는 것을 2단계에서 검토한다.

> **lerobot 의 `max_relative_target` 은 반드시 `None` 으로 둔다.** 그것도 같은 종류의 속도 클램프인데, 켜면 `send_action` 마다 `Present_Position` 을 다시 읽어 제어 주기가 떨어지고, 무엇보다 **안전 로직이 두 곳에 흩어진다.** 클램프의 단일 출처는 `safety.py` 다.

**(3) 추종 오차 감시** — 값을 자르지 않고 감시한다.

```
|명령각 − 실제각| > 15도 가 500ms 지속 → HOLD
```

서보가 보고하는 `Present_Position`과 우리가 쓴 명령각을 비교한다. 팔이 물리적으로 막히면 모터는 최대 전력으로 계속 밀어붙이며, SO-101의 플라스틱 기어는 수 초 만에 손상된다.

**즉시가 아니라 500ms 지속을 조건으로 하는 이유:** 빠르게 움직일 때는 관성 때문에 정상적으로도 명령각이 실제각을 앞선다. 순간 오차로 매번 HOLD가 걸리면 사용할 수 없다. "오차가 크다"가 아니라 "오차가 크게 유지된다"가 걸림의 신호다.

임계값 15도/500ms는 실기 검증(2단계)에서 조정한다.

### 5.5 워치독

**서버 (안전 담당)** — 20Hz로 검사

```python
if time.monotonic() - last_packet_time > 0.2:
    state = HOLD
```

200ms는 60Hz 기준 연속 12패킷 유실에 해당한다. 정상 회선에서 1~2개 유실은 흔하지만 12개 연속은 실제 단절 신호다.

200ms 동안의 위험은 제한적이다. 속도 클램프 때문에 팔로워는 **마지막으로 받은 목표각까지만** 이동하고 멈추며, 그 목표각은 200ms 전 조종자가 의도한 위치다.

**클라이언트 (인지 담당)** — 300ms 무수신 시 화면 전체에 빨간 테두리와 "연결 끊김" 표시.

로봇팔은 원래 느리게 움직이므로 정지 화면과 저속 화면이 몇 초간 구분되지 않는다. 조종자가 이를 모르고 리더를 계속 움직이면, 복구 순간 팔이 누적된 움직임을 따라잡으려 한다. 영상 **내용**이 아니라 **테두리**로 판별 가능해야 한다.

서버(200ms)보다 긴 300ms를 쓰는 이유는 서버가 먼저 조치하고 클라이언트가 그 결과를 확인하는 순서를 만들어 로그에서 원인을 구분하기 위함이다.

### 5.6 오래된 프레임 폐기

카메라 스레드는 최신 프레임 **1장만** 보유한다. 이전 프레임의 전송이 끝나지 않았으면 새 프레임으로 덮어쓰고 이전 것은 폐기한다.

큐에 쌓으면 영상이 점진적으로 뒤처져 결국 수 초 전 화면을 보며 조종하게 된다. 화질이 아니라 **최신성**을 지킨다.

### 5.7 각도 비교의 두 가지 용도 (구분 주의)

| | **정렬 오차** | **추종 오차** |
|---|---|---|
| 비교 대상 | 리더각 ↔ 팔로워 실제각 | 팔로워 **명령각** ↔ 팔로워 실제각 |
| 측정 범위 | 두 PC에 걸쳐 | 작업대 PC 내부에서만 |
| 질문 | "시작해도 되는가?" | "계속해도 되는가?" |
| 시점 | 연결 전 | 연결 중 |
| 결과 | engage 허용/차단 | HOLD |

| 파일 | 책임 | 의존 |
|---|---|---|
| `protocol.py` | 숫자 ↔ 바이트 변환, 상수 | **없음** |
| `safety.py` | 목표각 → 안전한 목표각 + 상태 | **없음** |

### 핵심 인터페이스

```python
# workbench/safety.py — 하드웨어도 네트워크도 건드리지 않는다
class SafetyGate:
    def step(self, packet: ControlPacket | None,
                   actual: list[float],
                   now: float) -> SafetyResult: ...

@dataclass
class SafetyResult:
    state: State
    targets: list[float]     # 팔로워에 실제로 쓸 각도
    flags: int
    reason: str | None       # HOLD 사유 (화면 표시용)
```

```python
# 팔 인터페이스 — 실물과 mock이 동일하게 구현
class FollowerArms(Protocol):
    def read_positions(self) -> list[float]: ...
    def write_positions(self, angles: list[float]) -> None: ...
    def set_torque(self, enabled: bool) -> None: ...

class LeaderArms(Protocol):
    def read_positions(self) -> list[float]: ...
```

`safety.py`와 `protocol.py`를 순수 함수로 유지하는 것이 이 설계의 핵심이다. **사고를 막는 로직 전부가 여기 있고, 로봇도 인터넷도 없이 노트북에서 100% 테스트 가능해진다.**

### mock

`fake_arms.py`는 실제 팔과 동일한 인터페이스를 가지되 시리얼 대신 메모리 변수에 각도를 저장한다. 명령각을 그대로 실제각으로 반환하는 기본 모드 외에, 테스트용으로 **걸림 시뮬레이션**(특정 각도 이상 안 움직임)과 **지연 시뮬레이션**을 제공한다.

`fake_cameras.py`는 프레임 번호와 캡처 시각이 그려진 합성 이미지를 생성한다. 화면에 표시된 프레임 번호로 영상 지연을 눈으로 확인할 수 있다.

`server.py`는 설정값 `use_mock: true` 하나로 실물/가짜를 교체한다. 이로써 문제 발생 시 mock으로 갈아끼워 네트워크 문제인지 하드웨어 문제인지 즉시 판별할 수 있다.

### 7.2 COM 포트와 캘리브레이션

**COM 포트를 설정에 직접 쓰지 않는다.** Windows의 COM 번호는 USB 재연결·재부팅으로 뒤바뀔 수 있으며, 좌우 팔이 뒤바뀌면 재앙이다. `serial.tools.list_ports` 의 USB 장치 시리얼 번호로 조회해 COM 포트를 찾는 헬퍼를 둔다. 시리얼 번호가 조회되지 않는 어댑터인 경우 기동 시 팔 식별을 사람이 확인하는 절차로 대체한다. 최초 식별에는 `lerobot-find-port` 를 쓴다.

**캘리브레이션 파일**은 각 팔의 인코더 raw 값과 각도의 매핑이다. 팔마다 조립 상태가 다르므로 4개 팔 각각에 대해 한 번 생성해야 한다. 이 파일이 어긋나면 정렬 절차가 무의미해진다.

생성은 lerobot 의 `lerobot-calibrate` CLI 로 한다. **우리 서버 안에서 캘리브레이션을 돌리지 않는다** — lerobot 의 `calibrate()` 는 `input()` 으로 사람에게 팔을 움직이라고 요구하는 대화형 절차이므로, 서버 프로세스에 들어가면 조종 루프가 멈춘다. 서버는 이미 만들어진 파일만 읽는다.

저장 위치는 `$HF_LEROBOT_CALIBRATION/robots/so_follower/<id>.json` 과 `.../teleoperators/so_leader/<id>.json` 이다(`id` 는 설정에서 주는 이름). 팔 4대의 `id` 는 `left`/`right` × 리더/팔로워로 구분한다.

## 9. 에러 처리

| 상황 | 동작 |
|---|---|
| 잘못된 magic | 파싱하지 않고 폐기, 로그 (레이트 제한) |
| 패킷 길이 불일치 | 폐기, 로그 |
| `seq` 역행 | 조용히 폐기 (정상 동작) |
| 제어 패킷 200ms 무수신 | HOLD |
| 서보 읽기/쓰기 실패 | 3회 재시도 후 HOLD + `MOTOR_ERROR` |
| 서보 버스 초기화 실패 | FAULT (토크 끔), 서버 계속 실행하며 상태 보고 |
| 카메라 열기 실패 | 해당 카메라만 비활성, 나머지는 정상 동작, 클라이언트에 "카메라 N 없음" 표시 |
| 카메라 캡처 실패 (일시적) | 해당 프레임 건너뜀 |
| TCP 영상 연결 끊김 | 서버는 재수신 대기, 클라이언트는 1초 간격 재접속. **제어 채널에는 영향 없음** |
| 클라이언트 종료 | 서버는 워치독으로 HOLD. **토크 유지**, DISCONNECTED로 내려가지 않음 |
| 클라이언트 재접속 | HOLD 유지. `cmd=RESET`을 받아야 ALIGNING으로 |
| 서버 재시작 | DISCONNECTED(토크 끔)부터 시작. 클라이언트가 자동 재연결 후 ALIGNING |

**공통 원칙: 어떤 오류에서도 로봇이 사람 확인 없이 자동으로 움직임을 재개하지 않는다.**

## 10. 테스트 전략

### 단위 테스트 (하드웨어·네트워크 불필요)

**`protocol.py`**
- pack → unpack 왕복 후 값 일치
- 각 패킷의 바이트 길이가 66 / 66 / 21인지
- 잘못된 magic, 잘린 바이트에 대한 거부
- `seq` 되감김 처리

**`safety.py`** — 가장 중요한 테스트 대상
- 정렬 오차가 임계값을 넘으면 ENGAGED로 가지 않음
- 임계값 안 + 클러치 → ENGAGED
- 클러치 해제 → 즉시 ALIGNING, 목표각이 마지막 적용각에 고정
- 큰 목표각 점프가 `max_step`으로 잘림
- 관절 한계 밖 목표각이 잘림
- 추종 오차가 임계값 미만 지속 시 HOLD 안 됨 / 초과 지속 시 HOLD
- 워치독 시간 경과 → HOLD
- HOLD에서 패킷이 정상 복구되어도 자동으로 벗어나지 않음
- HOLD에서 클라이언트가 완전히 사라져도 DISCONNECTED로 내려가지 않고 토크를 유지
- `cmd=RESET` 수신 시에만 ALIGNING으로 복귀. HOLD가 아닌 상태의 RESET은 무시
- 클러치가 이미 눌린 채 오차가 임계값 안으로 들어오면 engage되지 않음 (상승 에지 판정)

시간 의존 로직은 `now`를 인자로 받으므로 실제 대기 없이 테스트한다.

### 통합 테스트 (localhost)

- mock 서버 + mock 클라이언트를 한 프로세스에서 띄우고 왕복 지연 측정
- 인위적 패킷 유실·순서 뒤바꿈을 주입해 팔로워 궤적이 진동하지 않는지 확인
- 영상 프레임 프레이밍: 인위적으로 잘게 쪼갠 TCP 수신에서도 정확히 재조립되는지
- 프레임 폐기: 느린 수신자를 두었을 때 지연이 누적되지 않고 프레임이 버려지는지

### 수동 검증 (단계별, §11)

각 단계의 통과 기준을 충족해야 다음 단계로 넘어간다.

## 11. 단계별 검증 계획

각 단계에서 **새로 추가되는 변수는 하나뿐**이다. 문제 발생 시 원인 후보를 1개로 좁히기 위함이다.

### 1단계 — PC 1대, 전부 mock

서버(mock 팔, mock 카메라) ↔ localhost ↔ 클라이언트(mock 리더)

네트워크 계층, 안전 로직, 화면을 전부 완성한다. mock 리더가 사인파로 관절을 흔들고 mock 팔로워가 동일하게 따라오는지 확인. 하드웨어 없이 지금 시작 가능하며, 전체 코드의 대부분이 여기서 완성된다.

**통과 기준:** 왕복 지연 <5ms / 단위 테스트 전부 통과 / 24시간 연속 실행 후 크래시·메모리 증가 없음 / 워치독·클램프·정렬 시나리오 수동 확인

> **1단계 실제 결과 (2026-07-31):** 자동 테스트 114개 통과, 수동 검증 통과, localhost RTT <1ms.
> **24시간 연속 실행은 아직 하지 않았다.** 무인 운영(§1)으로 가기 전에 반드시 완료해야 하는 미결 항목이다.
>
> 1단계에서 실물 없이 발견해 고친 결함:
> 1. 제어 송신이 HUD 렌더링 스레드에 묶여 있어, 창이 멈추면 워치독이 오발동했다 → 송신 전용 스레드로 분리.
> 2. 제어·영상 소켓에 `SO_REUSEADDR` 을 걸어, Windows 에서 두 번째 서버가 조용히 같은 포트에 바인드해 제어 패킷을 가로챘다. 그 서버의 `last_seq` 가 높아 모든 패킷을 낡은 것으로 폐기했고, 조종자 화면은 DISCONNECTED 로 남거나 간헐적으로 HOLD 가 걸렸다 → 배타적 바인드로 변경, 두 번째 기동은 사유를 밝히며 실패한다.
> 3. 추종 오차는 '지난 프레임의 명령각'과 비교하므로 명령 직후 프레임에는 나타나지 않는다는 점을 테스트가 놓쳤다.

### 2단계 — PC 1대, 실제 팔 + 실제 카메라

개발 PC에 팔 4대와 카메라 3대를 모두 연결하고 localhost로 실행한다. **로봇 관련 문제를 여기서 전부 잡는다** — 캘리브레이션, COM 포트 고정, 영점 일치, 그리퍼 각도 매핑, 실제 달성 가능한 제어 주기, 관절 한계값·추종 오차 임계값 확정.

**통과 기준:** 리더를 움직이면 팔로워가 추종 / 정렬 절차 동작 / 클러치 해제 시 즉시 정지 / 팔을 손으로 막았을 때 추종 오차로 HOLD 진입 / 60Hz 유지

### 3단계 — PC 2대, 같은 LAN

개발 PC(클라이언트) ↔ 공유기 ↔ 작업대 PC(서버). 추가 변수는 실제 네트워크 인터페이스뿐이다 — 방화벽 규칙, 바인딩 주소(`0.0.0.0` vs `127.0.0.1`), 실제 소켓 동작.

**통과 기준:** RTT <20ms / 영상 3채널 정상 / 랜선 분리 시 200ms 내 HOLD, 화면 빨간 테두리 / 랜선 재연결 후 자동으로 움직이지 않고 ALIGNING 대기

> **3단계 진행 상황 (2026-08-03)**
>
> | 기준 | 결과 |
> |---|---|
> | 두 PC 사이 실제 조종 | ✅ 동작 확인 |
> | LAN RTT < 20ms | ✅ **15.0 ms** (단, Wi-Fi. 유선이면 1ms 미만) |
> | 랜선 분리 시 HOLD | ✅ 확인 |
> | 재연결 후 자동 시작 안 함 | ⬜ |
> | 호밍 실물 검증 (2단계 이월) | ✅ 확인 |
> | 영상 3채널 | ⬜ |
> | 24시간 소킹 (1단계 이월) | ⬜ |
>
> **호밍 목표 자세를 다시 잡으면서 `joint_limits` 의 의미를 바로잡았다.** 처음에는
> 캘리브레이션 기록 범위에서 8도를 깎았는데, 그것이 조종자가 실제로 쓰는 자세를
> 배제했다. 원인은 두 가지를 섞은 것이다 — `joint_limits` 는 **작업공간 제한**이고
> 끝단에 눌리는 것은 **추종 오차**가 잡는다. 또한 캘리브레이션 기록 범위는 기계적
> 한계가 아니라 그때 훑은 만큼일 뿐이다 (lerobot 의 도 변환은 값을 자르지 않아,
> `right_elbow_flex` 가 기록 ±96.7 을 넘어 97.1 로 읽혔다).
>
> 구성: 작업대 PC(Windows, Wi-Fi `192.168.0.3`)에 팔로워 2대, 개발 PC 에 리더 2대.
> 코드는 GitHub 로 동기화하고 캘리브레이션은 `tools/move_calibration.py` 로 옮겼다.
>
> **RTT 15ms 는 LAN 치고 높다.** ping 도 11~13ms 로, Wi-Fi 절전 모드가 원인으로 보인다.
> 기준은 통과했지만 여유가 5ms 뿐이고, 무선은 평균보다 **순간 튐**이 문제라 워치독(200ms)에
> 걸릴 수 있다. 작업대 PC 에 이더넷 어댑터가 있으므로 튐이 관측되면 유선으로 바꾼다.

### 4단계 — 인터넷 (집 ↔ 작업대)

포트포워딩과 공인 IP. 추가 변수는 NAT와 실제 지연뿐이다.

**통과 기준:** RTT <150ms / 30분 연속 조작 중 예기치 않은 HOLD 없음 / 유실률 화면 표시 정상 / 실제 실험실 작업 1건 완수

개발 PC(RTX 5090 장착 머신)는 1~2단계에서 서버 겸 클라이언트를 모두 담당하고, 3단계부터 집 PC 역할(클라이언트)을 한다. 작업대 PC는 3단계에 처음 필요하므로 지금 없어도 개발을 시작할 수 있다.

## 12. 후속 스펙 (이번 범위 아님)

- **다중 사용자** — 3명이 리더 2대씩 보유. 세션 점유·대기열·인증·강제 인수인계가 필요하다. 현 설계에서 서버는 "가장 최근에 유효 패킷을 보낸 주소"에만 응답하므로, 두 클라이언트가 동시에 보내면 제어권이 진동한다. **다중 사용자 스펙에서 반드시 명시적 세션 소유권을 도입해야 한다.**
- **데이터셋 기록** — LeRobotDataset 형식으로 세션 저장
- **힘 피드백** — 리더 암에 저항 전달
- **무인 운영 강화** — 원격 전원 제어, 물리적 E-stop 연동, 작업 공간 침입 감지
